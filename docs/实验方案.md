## 1. 两种架构的关键差异总结

| 维度 | 原始 Agent (`ship-violation-agent`) | 三级级联框架 (`ais_accelerator + triage_engine + llm_layer`) |
|------|------|------|
| **架构模式** | 4 个 LangGraph ReAct Agent 串行（规则→轨迹→AIS验证→编排） | 三级流水线：规则引擎→ML分类→LLM判定 |
| **LLM 调用次数** | 可疑船 ~4 次（预过滤通过则为 0） | 大多数船 ~0 次，最多 ~1 次 |
| **数据处理方式** | 单船单点 + 少量历史点，原样传 LLM | 批量载入 → 质控 → 分段 → 压缩 → 特征提取 |
| **轨迹压缩** | 无 | RDP 压缩 + 事件感知（500点→~10点） |
| **规则检测** | LLM 通过工具调用判断 | 纯算法规则引擎（0 LLM） |
| **分类机制** | 无 ML 分类，全部依赖 LLM 判断 | LightGBM 四分类 + 置信度分级路由 |
| **并行处理** | 船间并行（ThreadPoolExecutor） | L1 批量处理 + L2 批量路由 + L3 可选并行 |
| **优雅降级** | 有限（某 Agent 失败则返回 error dict） | 每层独立降级（Mock/无模型/无LLM均能跑） |
| **组件耦合** | 紧耦合（所有 Agent 在同一 LangGraph 图内） | 松耦合（每层独立包，可单独使用/替换） |

## 2. 实验一：实用性实验

### 2.1 实验目的

证明三级级联架构能够处理**真实世界的大规模 AIS 数据**，而原始 Agent 仅适用于小规模单船验证。

### 2.2 实验设计

#### 实验 A：数据容量压力测试

| 项目 | 内容 |
|------|------|
| **目的** | 对比两种系统在不同数据规模下的处理能力 |
| **测试数据** | 从现有 CSV（210724铜锣峡210731.csv）中提取 1/10/50/100/200 艘船的数据 |
| **测量指标** | ① 能否成功处理 ② 总处理时间 ③ 是否 OOM/超时 ④ CPU/内存峰值 |
| **通过标准** | 三级架构能处理 200 艘以上；原始 Agent 在 50 艘以上即显著退化或失败 |

**具体步骤**：

```
1. 准备 5 个测试子集（1/10/50/100/200 艘船）
2. 对每个子集：
   2a. 原始 Agent：python main.py --mode file --input data/test_Nships.csv --max-ships N
   2b. 三级架构：python run.py --input data/test_Nships.csv -n N --workers 4
3. 记录：处理时间、成功/失败状态、内存使用、LLM 调用总数
4. 绘制 "船舶数量 vs 处理时间" 曲线
```

#### 实验 B：真实轨迹数据溯源能力

| 项目 | 内容 |
|------|------|
| **目的** | 证明三级架构能处理完整轨迹数据并生成可追溯的分析报告 |
| **测试数据** | 现有 CSV（每船 50~500 个轨迹点） |
| **测量指标** | ① 轨迹分段数 ② 事件检测数 ③ 压缩率 ④ 证据链完整度 |
| **通过标准** | 三级架构输出包含：轨迹压缩报告、每个检测事件的时空范围、规则命中记录、质量报告；原始 Agent 仅有最终判定，无中间证据留存 |

**具体步骤**：

```
1. 用三级架构处理完整 CSV：python run.py -i data/sample.csv --no-llm
2. 用原始 Agent 处理同一 CSV：python main.py --mode file --input data/sample.csv
3. 对比输出：
   3a. 三级架构：输出包含 → 轨迹分段/质量报告/事件列表/压缩统计/特征向量
   3b. 原始 Agent：输出仅包含 → true/false 判定 + 置信度 + 简短评估
4. 结论：三级架构的"证据链完整性"远超原始 Agent
```

#### 实验 C：批量处理工作流完整性

| 项目 | 内容 |
|------|------|
| **目的** | 验证三级架构端到端工作流的自动化程度 |
| **测试数据** | data/input/ 下所有 CSV |
| **测量指标** | ① 自动格式转换 ② sqlite 缓存复用 ③ 逐船输出 ④ 汇总统计 |
| **通过标准** | 一键运行即可完成"读取→转换→加速→ML→LLM→保存"全链路 |

## 3. 实验二：速度性能实验

### 3.1 实验目的

定量证明三级级联架构处理速度显著快于原始 Agent。

### 3.2 关键加速原理

```
原始 Agent:
  输入 → [预过滤] → [规则Agent: 1 LLM调用+工具] → [轨迹Agent: 1 LLM调用+工具]
        → [AIS验证Agent: 1 LLM调用+工具] → [编排Agent: 1 LLM调用]
        = 可疑船: 4次LLM调用 / 正常船通过预过滤: 0次LLM调用

三级级联架构:
  输入 → [L1 规则引擎: 0 LLM] → [L2 ML分类: 0 LLM, <10ms]
        → [L3: 置信度≥0.9=0次调用 / 置信度<0.9=1次调用]
        = 大多数船: 0次LLM调用 / 少数可疑船: 1次LLM调用
```

### 3.3 实验设计

#### 实验 A：LLM 调用次数对比（理论下限 vs 实测）

| 项目 | 内容 |
|------|------|
| **方法** | 对同一批测试数据，分别统计两种系统的 LLM 调用总次数 |
| **测试数据** | 100 艘船的合成数据集（50% 正常 + 30% 可疑 + 20% 违规） |
| **测量指标** | ① 每船平均 LLM 调用次数 ② LLM 调用总数 ③ LLM 调用减少百分比 |
| **预期结果** | 原始 Agent：2.0~3.5 次/船；三级架构：0.1~0.5 次/船（减少 70%~90%） |

**实验步骤**：
```
1. 构造 100 条测试用例（含 ground truth）
2. 原始 Agent 运行：统计 _fast_prefilter 命中率 + LLM 调用次数
3. 三级架构运行：统计 routing 分布（direct/medium/low）+ LLM 调用次数
4. 计算对比：
   原始 Agent LLM 调用 = 预过滤跳过数×0 + 触发的船数×4
   三级架构 LLM 调用 = normal 数×0 + obvious_issue×1 + has_risk×1 + needs_review×1
5. 输出对比表格
```

#### 实验 B：墙钟时间对比（Wall-Clock Time）

| 项目 | 内容 |
|------|------|
| **方法** | 在同一硬件上分别运行两种系统，测量端到端处理时间 |
| **测试数据** | 10/50/100 艘船的实测 AIS 数据 |
| **测量指标** | ① 总处理时间 ② 每船平均时间 ③ 加速比（三级/原始） |
| **预期结果** | 三级架构比原始 Agent 快 3~10 倍（取决于 LLM 调用节省比例） |

**实验步骤**：
```
1. 确保同一硬件条件（CPU: 8核+, 内存: 16GB+, Ollama 运行在 GPU 模式）
2. 预热：每种系统先跑 5 艘船预热 LLM 缓存
3. 正式测量（重复 3 次取中位数）：
   原始 Agent: python main.py --mode file --input data.csv -n N
   三级架构:   python run.py --input data.csv -n N --workers 4
4. 记录时间构成：
   原始 Agent: [数据加载] + [预过滤: Xms] + [LLM工作流: Xms/船]
   三级架构:   [数据加载: Xms] + [L1加速器: Xms/船] + [L2 ML路由: Xms/船] + [L3 LLM: Xms/船]
5. 标注 LLM 调用在图中的位置，直观展示"三级架构跳过绝大多数LLM调用"
```

#### 实验 C：数据压缩对速度的贡献

| 项目 | 内容 |
|------|------|
| **方法** | 对比"有压缩"和"无压缩"的 LLM 调用耗时 |
| **测试数据** | 含长轨迹（500+ 点）的 AIS 数据 |
| **测量指标** | ① 压缩率 ② LLM 输入 token 数减少比例 ③ LLM 推理时间对比 |
| **预期结果** | 三级架构将 LLM 输入 token 减少 90%+，LLM 推理时间减少 50%+ |

**实验步骤**：
```
1. 挑选轨迹长度 >300 点的船舶 10 艘
2. 用三级架构压缩后送 LLM vs 原始数据直接送 LLM
3. 对比：
   - 输入 token 数（原始轨迹 vs 压缩后轨迹）
   - LLM 首 token 延迟
   - LLM 输出质量（判定一致性）
4. 结论：压缩不减质量，但显著降低延迟
```

#### 实验 D：可扩展性测试

| 项目 | 内容 |
|------|------|
| **方法** | 固定数据量，改变并行度，观察加速效果 |
| **测试数据** | 100 艘船的数据集 |
| **测量指标** | ① 不同 worker 数下的处理时间（1/2/4/8） ② 加速比线形度 |
| **预期结果** | 原始 Agent 受 Ollama 并发瓶颈限制（4 worker 封顶）；三级架构 L1 纯 CPU 计算可充分发挥多核 |

## 4. 实验三：容错率实验

### 4.1 实验目的

证明三级级联架构在组件失效、数据异常等故障场景下仍能稳定产出，而原始 Agent 在同等条件下会崩溃或产出不可用结果。

### 4.2 故障场景矩阵

| 故障场景 | 原始 Agent 行为 | 三级架构行为 |
|----------|----------------|--------------|
| LLM 不可用（Ollama 关闭） | 启动时 sys.exit(1) | Mock 模式自动降级，继续处理 |
| ML 模型文件缺失 | 无 ML 层，不适用 | 自动触发初始训练（`train_initial()`） |
| Milvus 数据库不可用 | 无 Milvus 层，不适用 | 优雅跳过 Milvus，仅用 pgvector/LightGBM |
| CSV 格式异常 | 可能解析异常退出 | 异常行自动标记无效，不中断 |
| 输入数据缺失关键字段 | 校验失败报错 | 自动填充默认值 + 标记警告 |
| 轨迹点全部异常 | LLM 可能产生幻觉回复 | 质量检测提前识别并标记 low quality |

### 4.3 实验设计

#### 实验 A：组件不可用测试

| 项目 | 内容 |
|------|------|
| **目的** | 验证系统在核心组件缺失时的行为 |
| **故障注入** | ① 关闭 Ollama ② 删除模型文件 ③ 禁用数据库 ④ 组合故障 |
| **测量指标** | ① 是否崩溃退出 ② 是否输出结果 ③ 输出中是否包含"降级"标记 ④ 降级后准确率变化 |
| **通过标准** | 三级架构在任意单组件故障下均能完成处理；原始 Agent 在 LLM 不可用时完全不可用 |

**具体测试用例**：

```
测试1: LLM 不可用
  - 原始 Agent: python main.py --mode file          → "Ollama 连接失败" + sys.exit(1)
  - 三级架构:   python run.py                        → Mock 模式 + 输出含 "mock_mode: true"

测试2: ML 模型文件缺失
  - 原始 Agent: 不涉及                                   → N/A
  - 三级架构:   python run.py + 删除 triage_model.txt    → 自动执行 train_initial()，继续运行

测试3: 数据库不可用
  - 原始 Agent: 不涉及                                   → N/A
  - 三级架构:   python run.py + Milvus 端口关闭          → 路由降级为 "ML-only"，跳过向量检索

测试4: 组合故障（LLM + 数据库同时不可用）
  - 三级架构:  L1 加速器正常跑 + L2 纯 ML 路由 + L3 Mock → 输出完整
```

#### 实验 B：数据质量异常测试

| 项目 | 内容 |
|------|------|
| **目的** | 验证两种系统对脏数据的鲁棒性 |
| **数据构造** | ① 缺失经纬度 ② 速度字段 NaN ③ 时间乱序/重复 ④ 空文件 ⑤ 编码错误 |
| **测量指标** | ① 是否崩溃 ② 有效数据处理比例 ③ 错误报告中是否标明异常原因 |

**具体测试用例**：

```
构造 5 种异常数据文件：

| # | 异常类型 | 构造方法 |
|---|----------|----------|
| 1 | 空文件 | 仅有表头无数据行 |
| 2 | 关键字段缺失 | 删除 mmsi/lon/lat 列 |
| 3 | 数值异常 | speed 填写 -999 / lat 填写 999 |
| 4 | 时间异常 | 全船时间戳重复 / 时间逆序 |
| 5 | 混合异常 | 50% 正常 + 50% 异常行 |

每种文件分别运行两种系统：
- 原始 Agent: python main.py --mode file --input error_type_N.csv
- 三级架构:   python run.py --input error_type_N.csv

记录：
1. 是否成功完成处理
2. 处理了多少条有效船舶
3. 是否在输出中标明了异常原因
4. 用户能否一眼看出"哪些船可信、哪些有数据问题"
```

#### 实验 C：边界情况测试

| 项目 | 内容 |
|------|------|
| **目的** | 覆盖极端边界条件 |
| **测试场景** | ① 单点轨迹（1 个 AIS 点）② 极高速度（999节）③ 极短时间内大量数据点 ④ 船舶反复进入/离开管制区 |

**预期结论**：
- 三级架构的 L1 质量检测会在早期识别极端值并打标记（`quality: poor`），不会让异常数据进入后续处理
- 原始 Agent 无数据质量检测层，异常值直接进入 LLM 推理，可能导致错误判定

#### 实验 D：错误传播与隔离测试

| 项目 | 内容 |
|------|------|
| **目的** | 验证单条船的处理失败是否影响其他船 |
| **构造方法** | 在 100 艘船的数据集中混入 5 条致命异常（如空文件、格式完全错乱） |
| **测量指标** | ① 总处理完成数 ② 异常船是否污染其他船的结果 ③ 是否跑完全流程 |

**预期结论**：
- 三级架构：船与船之间完全隔离（SQLite store 逐船迭代），异常船仅在自己的输出中标记 error
- 原始 Agent：也使用 ThreadPoolExecutor 隔离，但某船 LLM 调用超时会占用线程池资源

## 6. 预期结果总结表

### 实用性对比

| 测试项 | 原始 Agent | 三级级联架构 | 结论 |
|--------|-----------|-------------|------|
| 100 艘船处理 | 可能超时/内存不足 | ~2-5 分钟完成 | 三级架构胜 |
| 轨迹压缩 | 不支持 | 500→10 点 (95%+) | 三级架构特有能力 |
| 证据链完整性 | 仅最终判定 | 质控+分段+事件+特征+路由+LLM 全链路 | 三级架构胜 |
| 一键端到端 | 需手动数据预处理 | `python run.py` 全自动 | 三级架构胜 |
| 批量处理 | 支持（但慢） | 支持（快） | 三级架构胜 |

### 速度对比

| 测试项 | 原始 Agent | 三级级联架构 | 加速比 |
|--------|-----------|-------------|--------|
| LLM 调用/船 | ~2.0-3.5 次 | ~0.1-0.5 次 | **减少 70-90%** |
| 每船平均时间 | ~15-30 秒 | ~0.5-5 秒 | **3-10 倍加速** |
| 100 艘处理时间 | ~25-50 分钟 | ~2-5 分钟 | **5-10 倍加速** |
| 数据输入量 | 全部原始数据 | 压缩后 ~5% | 上下文节省 95% |

### 容错率对比

| 故障场景 | 原始 Agent | 三级级联架构 |
|----------|-----------|-------------|
| LLM 断连 | ❌ 启动失败 | ✅ Mock 降级 + 正常输出 |
| 数据异常 | ❌ 解析报错 | ✅ 标记异常行 + 继续处理 |
| 单个组件故障 | ❌ 整条流水线中断 | ✅ 该层降级 + 其余正常 |
| 模型文件缺失 | N/A（无 ML 层） | ✅ 自动训练初始模型 |
| 单船异常 | ⚠️ 可能阻塞线程池 | ✅ 完全隔离 |
| 错误可追溯性 | ❌ 仅 error 字符串 | ✅ 错误类型/位置/严重程度分级 |
