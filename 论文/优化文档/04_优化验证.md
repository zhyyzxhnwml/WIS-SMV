# 优化验证文档

> 对应结果：《03_优化结果》
> 目的：不是再报一遍数字，而是逐条论证「这次的改动凭什么可信、退路在哪、哪里还没验证」
> 文档状态：v1.1（2026-10-16，按「① 违规判断准确性 ② 级联是否又快又准」两条主线重整）

---

## 一、本档术语

| 术语 | 大白话解释 |
|---|---|
| **实现一致性校验** | 让「仿真算的策略」和「代码里真正跑的策略」逐条对齐。不一致就报错，防止论文里写着一个代码里根本不存在的策略。 |
| **向后兼容** | 改动之后，原来的调用方式行为不变。 |
| **一键退路** | 出问题能不改代码就退回原状。 |
| **口径一致性** | 同一个指标是不是用同一套统计方法算的。口径不同的数字不能放在一起比。 |
| **上界（oracle）** | 允许偷看答案调到最优，是对手的极限。 |
| **回归** | 改动之后再跑一遍原有检查，确认没弄坏别的东西。 |

---

## 二、验证框架

```
V1 实现可信 ── 代码里的策略和仿真里算的是不是同一个东西
V2 兼容可信 ── 旧调用方的行为有没有被静默改掉
V3 结论稳健 ── 换个规则场景、换个判据，结论还成立吗
V4 对手公平 ── 有没有给现役判据最有利的条件
V5 负结果可信 ── 大模型那两轮没达标，有没有如实记录、而不是换个口径算到好看
V6 口径纪律 ── 报出来的成本数有没有写清它到底在数什么
V7 口径一致 ── 用来下结论的历史产物是不是同一版
```

## 三、V1 实现一致性验证（本轮最关键的一条）

**要防的问题**：仿真脚本里算的是 S3（无候选事件才调），而代码里可能还是旧判据——或者反过来。两边的数不一样，论文里就会写着一个代码里根本不存在的策略。

**做法**：让脚本**调用真实的 `TriageRouter.route()`**（不是自己手写一遍判据），把它的 `needs_llm` 与仿真结果**逐船**比对。

**实测输出**：

```
[实现校验] 真实 router 的 needs_llm 与『n_events==0』逐船一致：通过（调用 65/240 = 27.1%）
```

- **逐船 0 条不一致**（240 条全对）
- 调用数 **65/240 = 27.1%**，与仿真表里 S3 的 65 次完全吻合

**结论**：论文里写的 S3 就是代码里真正跑的判据。

## 四、V2 向后兼容验证

**要防的问题**：生产链路里可能有别的调用点（例如编排器），改默认值会让它们的行为**静默变化**——不报错，只是结论变了。

**做法**：不传新参数调用一次，检查是否仍走旧判据。

**实测输出**：

```
[兼容性校验] 不传 n_events 时仍走风险分判据：needs_llm=True（risk_score=0.030300 vs 阈值 0.00088）
```

**结论**：`n_events` 不给时行为与改动前**完全一致**；只有生产路径显式传入时才走新判据。

## 五、V3 结论稳健性验证

| 稳健性检查 | 做法 | 结果 |
|---|---|---|
| **换违规类型** | 分别摘掉「让路失败」与「违规追越」两类规则 | ✅ S3 在三个场景（完整 / 摘让路 / 摘追越）**全部**不低于现役判据 |
| **换候选判据** | 同时测了 7 个判据（S0/S1/S2/S3/S7/S5/S6） | ✅ 只有 S3 在三个场景里全都赢；S2 在场景 (b) 崩到 31.9%，S7 在场景 (c) 掉回 64.3% |

**为什么必须做「换候选判据」**：如果只试一个判据，赢了也不知道是判据好还是运气好。7 个一起测，才能说清「S3 是唯一稳健的那个」。

## 六、V4 对手公平性验证

| 给现役判据的有利条件 | 结果 |
|---|---|
| S6 允许**用真值在评测集上把风险分判据的阈值调到最优**（这是作弊上界） | 在场景 (c) 上只有 75.0%（等于「一次都不调」）；在场景 (b) 上要多花 **2.8 倍**调用才勉强超过 S3 |
| 现役判据在三个场景里都用**同一个生产阈值**（不算它吃亏） | S3 仍然全面胜出 |

**结论**：即使给现役判据最好机会，新判据仍然在成本和质量的联合意义上更优。而且——

> **S3 是免阈值的**：它没有任何需要标定的旋钮。这在工程上比 S6 强得多——S6 的「最优阈值」是在评测集上挑出来的，换一批数据就失效。

## 七、V5 负结果可信性验证

追加的两轮（O5/O6）都没达标，验证的是「这个结论本身可不可信」：

| 检查 | 结果 |
|---|---|
| 是不是只试了一种做法就下结论？ | ❌ 不是。O5 给了算好的几何量值，O6 把判定过程逐步写清，两种攻击方向都试过 |
| 是否给了公平的对照？ | ✅ O6 与「同一条规则用代码执行」直接对照：**70.6% vs 100%（且 0 token）** |
| 结果是否如实写入结论？ | ✅ 明确写为「⚠️ 未达 L1 水平 / 退化为平凡分类器」，不粉饰 |

**结论**：大模型那一级的天花板是**机制性**的（模型无法像代码那样严格执行数值比较），不是「提示没写好」——这一条本身就是可写进论文的发现。

| 检查 | 做法 | 结果 |

## 九、V7 口径一致性验证（为什么组合门控不下定量结论）

**要防的问题**：拿不同口径的历史产物算出来的数字当真，得出错误结论。

**做法**：在算「无事件 或 风险分高」的组合门控之前，先检查历史产物里 `needs_llm` 字段与「按风险分算出来的结论」是否自洽。

**实测（三个产物目录）**：

| 产物目录 | 船-日 | 有 `needs_llm` 字段 | 其中 True | 风险分 ≥ 0.000880 |
|---|---|---|---|---|
| `cascade_prod_newl2` | 5,543 | 1,357（仅 24%） | **16.3%** | **93.9%** |
| `cascade_prod` | 13,702 | 13,702（全部） | 44.2% | 51.8% |
| `cascade_prod_gate` | 372 | 372（全部） | 16.9% | 94.6% |

**发现**：在 `cascade_prod_newl2` 里，存了 `needs_llm` 的那批记录只有 16.3% 为 True，而按风险分算 93.9% 都该过阈值——**两者严重不自洽**，说明这批产物与当前门控口径不一致（大概率生成于门控标定之前）。

**处置**：**拒绝据此下组合门控的定量结论**，在结果文档里明确标注「留作后续工作」。

> 这条验证的价值在于：它挡住了一个看起来合理、实则建立在错误前提上的结论。

## 十一、V9 解析器健壮性验证 —— 一个「静默失败」的实例

这一节记录本轮发现并修掉的一个**最危险的 bug 类型：不报错、只是数字难看**。

### 11.1 现象

臂 I（判据写成提示 → LLM）跑出来：精确率 46.7%、**召回 5.8%**、F1 10.4%。
看起来像「让模型执行规则反而更差了」，是一个可以直接写进论文的结论。

### 11.2 但它是假的

抽查原始回答发现，模型把提示里 JSON 格式示例的外层花括号**原样抄了回来**：

```
{{"violation_detected": true, "violation_type": "give_way_failure", ...}}
```

而解析器取「第一个 `{` 到最后一个 `}`」得到 `{{...}}`，**不是合法 JSON** → 解析失败 → 按约定记为「未检测到违规」。

于是模型其实判对了，却被记成漏报。**240 条里有 222 条是这种情况。**

### 11.3 为什么这个 bug 危险

| 特征 | 说明 |
|---|---|
| 不报错 | 脚本正常退出，指标正常打印 |
| 方向一致 | 所有失败都记成「未检测到违规」，于是**召回被系统性压低**，看起来像一个「真的变差了」的结论 |
| 可骗过一切 | 如果不抽查原始回答，这个假结论就会进论文 |

### 11.4 修法（两层）

1. **解析器容忍双花括号**：把「原样」和「剥一层花括号」两种候选都试一遍。
2. **原始回答必须落盘**：所有臂的记录里都存 `raw` 字段——否则事后无法复核（臂 G 原本没存，本轮补上）。

### 11.5 污染范围核查

| 臂 | 解析失败数 | 结论 |
|---|---|---|
| D / E / F / G / H | **0 / 240**（每臂） | ✅ 未受影响 |
| **I** | **222 / 240** | ❌ 结果作废，重跑 |

**用新解析器重新解析 D/E/F/H 的缓存，与旧结果逐条比对：0 条不一致** → 证明这五个臂的结果确实未受影响。

### 11.6 修复后的结果

| | 修复前（假） | 修复后（真） |
|---|---|---|
| 臂 I 精确率 | 46.7% | **56.2%** |
| 臂 I 召回 | **5.8%** | **95.0%** |
| 臂 I F1 | 10.4% | **70.6%** |

**结论从「让模型执行规则反而更差」翻转为「模型执行同一条规则只有 70.6%，远低于代码执行的 100%」**——后者才是正确的、也更有价值的结论。

> 这一条验证的价值：它挡住了**一个方向一致、看起来很合理的假结论**。

### 11.7 附带发现：并行推理的非确定性

臂 G 在重跑前后 F1 从 71.8% 变成 73.1%（`temperature=0`、`seed=0` 固定）。
原因是 Ollama 的 `NUM_PARALLEL=2` 会把不同请求放进不同批处理槽位，浮点累加顺序不同 → 输出可能有细微差异。

**这对论文的影响**：单次运行的绝对值有小幅抖动（约 1~2 pt），但**不影响结论方向**（六个大模型臂的排序稳定、且全部远低于 L1 的 100%）。
论文里应写明「本地推理在并行槽位下非严格确定性」这一限制。

## 十三、未验证项与下一步（必须写进论文/交接）

### 未验证项 1：容器内复测线上口径

按既定流程「宿主侧实验 → 指标确认变好 → 更新进容器 → **复测线上口径**」，最后一步**尚未执行**。

**为什么要紧**：本轮的「指标变好」全部是**宿主侧离线**算的。线上口径（真实请求、真实并发、数据库与向量库参与）还没复测过。

**另外已知的部署差距**（需一并处理）：
- 容器镜像构建于 **2026-10-10**，而宿主关键文件更新于 **2026-10-14**：
  - 容器 `triage_model.txt` 1,772,776 字节（旧合成模型）vs 宿主 1,259,192 字节（真实重训模型）
  - 容器 `router.py` **没有** `risk_score` 字段（0 处）vs 宿主 6 处
  - 容器**没有** `triage_engine/window_feat.py`
- 也就是说：**容器落后不止本轮这一个改动，而是落后了多个版本**。重建镜像时要注意，仓库里有多个文件、约 8,600 行未提交的改动会一并被打进镜像。

### 未验证项 2：真实数据上的端到端复测

本轮 O3 只算了**调用率**（不需要调大模型）。真实数据上「新门控 + 大模型」的**端到端质量**没有测——那需要对真实数据上的船-日逐条调用大模型，机时量级不可行（约 15 小时）。

### 未验证项 3：组合门控的阈值标定

结果文档已说明为什么不下结论（历史产物口径不一致）。下一步需要：在**同一版门控口径**下重新生成一份产物，再算组合门控的成本-召回曲线，并把阈值按域标定。

### 风险提示（给使用者的三条）

1. **新门控默认已启用**（`GATE_MODE=evidence`）。若担心真实数据上把该看的船挡在门外，**改环境变量 `GATE_MODE=risk` 即可一键退回**，不需要改代码。
2. **不要单独用新门控处理规则覆盖差的域**：真实数据上 L1 报掉了 91% 的船，「无候选事件」≈「安静的船」。
3. **组合门控的阈值尚未标定**，上线前必须按目标域标定。
