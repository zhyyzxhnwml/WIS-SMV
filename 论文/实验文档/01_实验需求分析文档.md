# 实验需求分析文档

> 项目：船舶交通流智能体违规判断系统（智海巡航，`E:\AIS`）
> 目的：为 SCI 论文提供「可被审稿人接受」的实验依据
> 文档状态：v1.0（2026-10-15）

---

## 一、名词先说明白（本文档用到的专业术语）

看后面的内容之前，先把几个词解释清楚，否则读不懂需求在说什么。

| 术语 | 英文 | 大白话解释 |
|---|---|---|
| **真值 / 标注** | Ground Truth (GT) | 「标准答案」。要知道系统判得对不对，必须先有一份**跟系统无关的**正确答案。 |
| **循环论证** | Circular ground truth | 拿系统自己的输出当标准答案，再拿它证明系统好。等于自己出题自己判卷，结论无效。这是本文要**首先避开**的致命问题。 |
| **级联** | Cascade | 「接力赛」式多级处理：便宜的层层先过滤，只有少数疑难样本才交给人/大模型。本文是三级——规则引擎 → 机器学习筛查 → 大语言模型终裁。 |
| **基线** | Baseline | 「对照组」。论文里必须拿自己的方法和**别人已发表的方法**在同一块地上比，否则说「我们好」没有意义。 |
| **注入 / 合成场景** | Injection / Synthetic scenario | 用程序**故意造出**已知参数的违规场景（例如「最近会遇距离 0.1 海里、没有采取避让动作」），因为真实 AIS 数据里没有「违反第几条」这种逐条标注。 |
| **异常检测** | Anomaly Detection | 一类算法思路：不告诉它什么叫违规，只管找出「跟大多数船不一样」的船。LOF / iForest / VAE 都属于这一类。 |
| **P（精确率）/ R（召回率）/ F1** | Precision / Recall / F1 | 精确率＝报出来的里面有多少是对的（别冤枉人）；召回率＝真正的违规里抓到了多少（别漏掉）；F1 是两者的调和平均，一个数同时看两头。 |
| **AUC** | Area Under ROC Curve | 衡量「排序能力」：随便抽一条违规和一条正常，系统给违规打分更高的概率。0.5 = 瞎猜，1.0 = 完美，**小于 0.5 = 方向反了**。 |
| **oracle 阈值** | Oracle threshold | 「作弊阈值」：允许在测试集上直接挑一个让分数最高的门槛。这是**上界**（最好情况），报出来是为了给对手最有利的机会。 |
| **@1% 误报率召回** | Recall@1%FPR | 在「每 100 条正常船最多误报 1 条」这个能上线的诚实工作点上，能抓到多少违规。不碰答案，是真实可用的数字。 |
| **帕累托支配** | Pareto dominance | A 方案在**每一项指标上都不差、至少一项更好**，就说 A 支配 B。本文要证明级联在「成本」和「质量」两个维度上同时不输。 |
| **消融** | Ablation | 「拆零件」实验：把系统的某个部件去掉，看分数掉多少，以此证明这个部件有用。 |
| **显著性检验** | Significance test | 判断「我们的分数高是真实差距还是运气」。p 值小于 0.05 通常认为差距真实存在。 |
| **token** | Token | 大语言模型处理文本的最小单位（约等于 0.75 个英文单词 / 1~2 个汉字）。**token 数就是调用大模型的「油费」**，本文全部实测，不估算。 |
| **可复现性** | Reproducibility | 换个人、换台机器，照文档跑一遍能得到同样的数字。SCI 的硬要求。 |

## 二、为什么要做这批实验（背景）

现状是：系统已经做出来了，但要投 SCI，必须回答审稿人会追问的三句话：

1. 「**你说你的系统判得准，凭什么？**」——需要一份**不循环**的标准答案，以及和**别人已发表方法**的对比。
2. 「**三级级联听起来很新，但真的有必要吗？直接调大模型不行吗？**」——需要量化「级联在什么成本下拿到什么质量」，即成本-质量曲线。
3. 「**你报的分数是不是挑对自己有利的任务、或者照测试集调出来的？**」——需要有证伪性证据（门槛扫描、跨数据集体检、拆零件的消融）。

这三句话分别对应论文的三个主张（Claim），也就是下面需求的来源。

## 三、需求清单（每条都写成「可验证」的形式）

> 写法说明：一条需求如果不能被某个实验**明确地证实或证伪**，它就不该写进来。

### R1 违规判断能力必须有可比的外部参照

- **要什么**：在同一批样本、同一份标准答案上，把我们的系统与文献方法逐条比较。
- **为什么**：只报自己的分数不构成证据。
- **验收标准**：产出「方法 × 精确率/召回率/F1/AUC」的对照表；我们对每个对手的差值都有置信区间。
- **对应产物**：`论文/实验结果_汇总.md` 表 1。

### R2 级联的成本-质量关系必须被量化

- **要什么**：画出「调用大模型的比例」与「判定质量」的关系，并给出帕累托前沿。
- **为什么**：级联的价值主张就是「同样的质量花更少的钱（或者同等钱拿到更好质量）」。不画曲线就没有价值主张。
- **验收标准**：横轴为成本（调用次数 / token 数），纵轴为 F1，给出可操作的工作点建议。
- **对应产物**：表 2、表 3、`fig_pareto.png`。

### R3 与文献对比必须同口径，禁止直接抄文献数字

- **要什么**：文献方法必须**在本地重新实现并在我们的评测集（违规判断任务）上重跑**；文献原报数字不作为对比依据。
- **为什么**：文献的 F1 是在它们各自的数据集、各自的任务定义下测的，正负样本比例、特征口径都不一样。直接搬进对比表，审稿人一问「你们的 F1 和他们的 F1 是同一个东西吗」就崩；不同任务定义下的数字放在一起更不成立。
- **验收标准**：对比表里每个对手都是本地复现值，并注明超参来源（oracle 阈值 = 对对手最有利的上界）。
- **对应产物**：表 1。

### R4 标准答案必须与我们的实现无关（禁止循环论证）

- **要什么**：真值只能来自场景设计时人为给定，并用**独立参照实现**回放校验。
- **为什么**：系统自己的规则输出当答案，等于把结论写进前提。
- **验收标准**：能说清每条真值的来源链条；且存在一个「不是我们写的」校验环节。
- **对应产物**：注入集用 `benchmark/reference/colreg_ref.py`（独立实现）校验。

### R5 结论必须有统计显著性，不能只报点估计

- **要什么**：成对检验 + 置信区间，并披露多组结果（不挑好看的报）。
- **为什么**：差 3 个百分点可能是抽样抖动。
- **验收标准**：给出 McNemar 精确检验的 p 值与配对自助（bootstrap）95% 置信区间。
- **对应产物**：`论文/显著性检验.md`。

### R6 全流程必须可复现、可中断续跑

- **要什么**：一条命令重跑一个实验；机器断电后重启同一条命令从断点继续。
- **为什么**：本机随时可能关机；且 SCI 要求可复现。
- **验收标准**：所有长任务逐条/逐日落盘，带缓存指纹（数据或代码变了就自动重建，避免静默复用旧结果）。
- **对应产物**：`reproduce/` 下全部脚本 + `README.md`。

### R7 必须做证伪性设计（回应「你是不是照测试集调参」）

- **要什么**：(a) 门槛敏感度扫描；(b) 拆零件消融。
- **为什么**：审稿人最常质疑的就是「这一堆门槛是不是照着测试集调出来的」。
- **验收标准**：门槛扫描显示峰值位于生产取值处或其邻位、两侧下降。
- **对应产物**：表 4（门槛扫描）、表 5（规则覆盖消融）。

### R8 必须如实报告能力边界与负面结果

- **要什么**：明确写清系统在哪些类别上抓不到、哪个部件当前有缺陷。
- **为什么**：完美无缺的结果反而不可信；如实报告边界是加分项。
- **验收标准**：给出「按类别分组的召回」，暴露系统覆盖不到的类型；给出部件缺陷的量化。
- **对应产物**：表 5（规则覆盖消融，含分组召回与 L2 缺陷量化）。

## 五、明确「不做什么」（范围边界）

需求分析不仅要写做什么，也要写**不做什么**，否则范围会失控。

| 不做 | 原因 |
|---|---|
| 不做双人人工标注 + κ 一致性检验 | 人力成本超出本轮范围。**这是本批实验最主要的已知缺口**，若审稿人质疑「合成数据」，需补做。 |
| 不做实时在线部署测试 | 论文主线是离线可比实验；在线性能（时延、吞吐）只作为附注给出实测值。 |
