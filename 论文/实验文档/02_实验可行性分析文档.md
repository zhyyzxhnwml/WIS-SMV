# 实验可行性分析文档

> 对应需求：《01_实验需求分析文档》中的 R1–R8
> 目的：逐项论证「这些实验在本机、本轮时间内、用现有数据**能不能真的做出来**」
> 文档状态：v1.0（2026-10-15）

---

## 一、本档补充术语

| 术语 | 大白话解释 |
|---|---|
| **注入生成器** | 一段程序，把「违规动作」按已知参数合成到真实船的轨迹旁边，从而**制造出带标准答案的样本**。 |
| **独立参照实现** | 为同一个物理判据**再写一遍**、但**不共用代码**的计算程序。它的作用是「对答案」：如果两套实现独立地都算出「最小会遇距离 0.12 海里」，那这个数才可信。 |
| **窗口（window）** | 把一天的轨迹切成一段一段（本文是 20 分钟一段），每一段作为一个判定的最小单元。 |
| **锚点（anchor）** | 在事故真值里**唯一精确**的那个时刻（报告里写的「几点几分出的事」）。用它来对齐正样本窗口，比用报告给的「大致时间段」准得多。 |
| **缓存指纹** | 给输入数据与代码版本算一个「身份证号」。下次跑的时候对不上就**自动重建**，避免读到过期的中间结果。 |
| **上下文长度（num_ctx）** | 大模型一次最多能「看到」多少 token。超了会被**静默截断**（不报错，只是模型看到的是半截轨迹）。 |
| **显存溢出（OOM）** | 显卡内存不够，系统把一部分计算挪到 CPU，速度骤降。 |
| **无监督** | 训练时**只用正常样本**、不给标签。LOF/iForest/自编码器类方法都是这种用法，这是文献的规矩，不能给它们喂标签。 |
| **标签泄漏** | 特征里混进了「只有知道答案才能算出来」的信息，导致分数虚高。 |

## 二、数据可行性

### 2.1 注入集（违规判断的主战场）—— ✅ 可行

| 检查项 | 结论 |
|---|---|
| 源数据是否存在 | ✅ `data/input/_fzais1009_converted.csv`（约 59 MB，真实 AIS 轨迹） |
| 生成器是否可用 | ✅ `benchmark/inject_violations.py`（905 行，含场景谱与自校验） |
| 能否产出标准答案 | ✅ 生成 `inject_v1.csv` + `inject_v1.gt.json` 一对，真值里写明每条船「该不该违规、违反哪一条、目标船是谁」 |
| 真值是否与我们实现无关 | ✅ 每个场景用 `benchmark/reference/colreg_ref.py`（**独立参照实现**）回放校验实际最小会遇距离，对不上设计值的样本直接丢弃 |
| 实际规模 | 240 场景 = 120 违规（72 让路失败 + 48 违规追越）+ 120 合规；进场 452 船 / 421,609 行 |
| 正负是否平衡 | ✅ 严格 120 : 120，因此「全判违规」的平凡 F1 = 66.7%（一个重要的参照线） |

**为什么必须平衡**：如果违规船只占 1%，那么「全判正常」就能拿到很高的准确率，所有方法看起来都「差不多」，区分度消失。正负各半能让 F1 的差异最大化暴露。

### 2.2 HawaiiCoast_GT（外部体检）—— ✅ 可行

| 检查项 | 结论 |
|---|---|
| 真值文件 | ✅ `实验数据/HawaiiCoast_GT_GitHub/hawaii_primary_trajectories_of_interest_2017_2020.csv`（18 列，208 行 / 154 起事故 / 145 船） |
| 真值来源 | ✅ 美国海岸警卫队事故调查报告（IIR）+ 人工比对 AIS 航迹，**与我们的实现完全无关** |
| 点级 AIS 数据 | ✅ 已下载 178 天 MarineCadastre 日包（`data/public/marinecadastre/hawaii/*.csv.gz`） |
| 能否构建评测集 | ✅ `benchmark/hawaii_eval.py --build`，逐日可续跑；实际建成 **11,064 个 20 分钟窗（144 正 / 10,920 负，覆盖 182 天）** |
| 正例占比 | 1.30% → 「全判异常」的平凡 F1 上限 = 2.57%（又一条重要参照线） |

**已知的数据缺陷（必须在论文里如实写）**：
报告给出的 `ais_incident_start/end_bound_hst` 是**外边界**（中位跨度 17.34 小时，覆盖大半个白天），不是事故时刻。拿它当正样本，绝大多数正窗里其实什么都没发生 → 所有方法一起掉到随机水平。本实验**改用报告时刻 `report_incident_time_of_interest_hst` 作为锚点**（±1 小时取最近的至多 3 个窗），才让任务良定义。没有可用锚点的事故一条正样本都不出——**宁可少，不要错的**。

### 2.3 `实验数据/` 里那 5 篇 LLM Agent 安全论文 —— ❌ 与本任务不可比

| 论文 | 本地有什么 | 能不能跑 | 结论 |
|---|---|---|---|
| **AgentDojo**（Debenedetti 2024, MIT） | 完整源码 99 个 .py | 技术上能跑 | 但它的任务是「LLM Agent 在银行/邮箱等工具环境里是否被提示注入」。**与船舶轨迹无关**，跑出来的数进不了我们的表 |
| **R-Judge**（Yuan 2024） | 只有 zip（2.53 MB，未解压） | 需解压；仓库未声明许可 | 评测对象是 LLM 的风险识别能力，且论文用 GPT-4 当自动评分器（有 API 成本）。与本任务正交 |
| **AgentAuditor / ASSEBench**（Luo 2025） | 只有 zip（8.16 MB） | 需解压 | 同上 |
| **GuardAgent**（Xiang 2025） | code.zip + dataset.zip | ❌ 真正的数据在 Google Drive，本环境不可达 | 不可行 |
| **AgentHarm**（Andriushchenko 2025） | **只有 PDF**，无数据无代码 | ❌ | 只能引用 |

**可行性结论**：这 5 篇**在「证明船舶违规判断能力」这件事上不可行**，因为：
1. 任务对象不同（文本化的 agent 交互记录 vs 船舶时空轨迹）；
2. 评价体系不同（是否有害/是否被越狱 vs 违反哪条避碰规则）；
3. 一半以上连数据都拿不到。

**正确处理方式**：写进 Related Work（相关工作）说明差异，**不放进对比表**。对比表只放**同任务、同真值**的方法——即 8 个无监督异常检测器。

> 唯一的例外情况：如果导师坚持要「和这 5 篇比」，唯一站得住的做法是把 **L3（大模型判定模块）单独拉出来**，用它们的数据集测「风险识别 F1」。但那**不能证明船舶违规判断更好**，且需要解压 zip + GPT-4 评判（成本）。建议放 Discussion 一小段，不做主实验。

### 2.4 人工标注 GT —— ❌ 本轮不可行

需求文档里说的「双人独立标注 + 第三人仲裁 + Cohen's κ ≥ 0.70」，需要：至少 1,000 条样本 × 2 名标注员 × 至少 2 轮（含仲裁），且标注员需具备避碰规则知识。**本轮无此人力**，列为已知缺口。

## 三、算力可行性

### 3.1 大模型（L3）—— ✅ 可行，但有两个必须处理的坑

| 检查项 | 实测结果 |
|---|---|
| 推理服务 | ✅ Ollama（本机 `127.0.0.1:11434`） |
| 模型 | ✅ `qwen2.5:7b-instruct-q4_K_M`（4.7 GB，Q4_K_M 量化） |
| 显卡 | ✅ NVIDIA RTX 4060 Laptop，8 GB 显存（6.9 GB 可用）；实测 **29/29 层全部卸载到 GPU** |
| 单次调用时延 | ✅ 预热后 **3.6 秒**（约 2,800 prompt token 的提示） |
| 并发吞吐 | ✅ `OLLAMA_NUM_PARALLEL=2` 时，两次并发总墙钟 3.8 秒 → **吞吐约 2 倍**；`=3` 时三次并发各 53 秒 → **反而变慢 15 倍**（显存溢出，KV 缓存被挤到 CPU）。**结论：并行度固定为 2。** |

**坑 1：模型目录**。本机的模型并不在默认目录，必须显式指定环境变量：
```
OLLAMA_MODELS=E:\model
```
否则 `/api/tags` 返回的模型清单是空的、`/api/chat` 直接返回 **404 model not found**。（排查耗时约 20 分钟，已记录在 `experiments/paper/README.md`。）

**坑 2：上下文静默截断**。Ollama 按显存自动推算的默认上下文只有 **4096 token**，而本任务的提示（本船 + 3 条邻近船 × 20 个轨迹点）可达 2,800~5,100 token。超长会被**静默截断**——不报错，只是模型看到的是半截轨迹，结论悄悄变差。
**对策**：请求里显式写 `num_ctx = 8192`，所有对照臂统一。

### 3.2 传统方法（8 个文献基线）—— ✅ 可行

| 检查项 | 结论 |
|---|---|
| 依赖 | 只用 `numpy` / `scikit-learn` / 自实现的浅层与深度自编码器，纯 CPU 可跑 |
| 单方法耗时 | 经典方法 0~4 秒；深度方法每个约 **50~1,285 秒**（120 轮训练，取决于是 VAE 还是 Transformer-LSTM） |
| 能否续跑 | ✅ 每个方法跑完即落盘，中途关机重跑会自动跳过已完成的 |

### 3.3 统计检验 —— ✅ 可行（自实现，无外部依赖）

- **McNemar 精确检验**：用组合数直接算二项分布双侧 p 值。样本量小时必须用精确版，卡方近似不成立。
- **配对自助（bootstrap）置信区间**：重采样**样本对**（保持配对结构）2,000 次，取 2.5/97.5 分位。配对重采样而不是各自重采样——后者会高估方差。

### 3.4 成本计量 —— ✅ 可行

Ollama 原生接口 `/api/chat` 的响应里带有 `prompt_eval_count`（提示消耗 token）与 `eval_count`（生成消耗 token），是**实测值**。不使用「字符数 ÷ 4」这种估算——估算会让成本对比失去说服力。

> 注意：项目原有的 `llm_layer/handler.py` 走的是 LangChain 封装，**拿不到这两个字段**。因此对照臂实验另走原生接口，这是必要的一次性开发。

## 六、可行性结论

| 维度 | 结论 |
|---|---|
| 数据 | ✅ 两套独立真值可用：注入集（违规判断）+ HawaiiCoast_GT（外部体检） |
| 算力 | ✅ 本机可完成全部对照臂；并行度固定 2；两个环境坑已有明确对策 |
| 方法 | ✅ 8 个基线本地可复现；统计检验自实现；成本可实测 |
| 时间 | ✅ 全部实验合计约 6~8 小时机时，且**任意时刻可中断续跑** |
| 范围 | ⚠️ 5 篇 LLM Agent 安全论文不可比（已说明）；人工标注 GT 本轮无法做（已知缺口） |

**总体结论：R1–R8 需求在本机、本轮时间内均可实现，实验方案可行。**
唯一需要向审稿人主动交代的是「合成/注入真值 + 未做人工标注」这一缺口，对策是**用第三方公开真值（Hawaii）做交叉体检**，并如实报告我们在那份真值上并不占优——这本身也是「没有挑对自己有利的任务」的证据。
